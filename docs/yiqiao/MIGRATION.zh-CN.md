# 迁移到 YiQiao

**简体中文** | [English](MIGRATION.md)

本指南介绍如何从早期自托管开发版本或其他 Compose 安装迁移到 YiQiao，不提供
托管服务的自动导出功能。对于尚未保存在本地 PostgreSQL、Neo4j 和 history 存储中的
数据，请使用控制台聊天记录导入器或受支持的导出流程。

## 迁移前准备

记录以下信息：

- 源提交或镜像摘要。
- Compose 项目、服务、网络和卷名称。
- PostgreSQL 用户和两个数据库名称。
- 是否启用了 Neo4j 图记忆。
- 公共 URL、反向代理配置、服务商路由和嵌入维度。
- 管理员、项目、API 密钥、保留策略、配额、Webhook 和导入状态。

按照[运维指南](OPERATIONS.zh-CN.md)创建并测试完整备份。不要在只有唯一一份源卷数据的
情况下继续。

## 配置迁移

运行 YiQiao 初始化器以创建新的环境文件。不要整体复制旧 `.env`；这样可能重新引入
弱密钥、公开数据库绑定、已关闭的身份验证、过期镜像名称或失效的服务端点。

```bash
git clone https://github.com/daizhongming/YiQiao.git
cd YiQiao
./scripts/init.sh
```

PowerShell 用户运行
`powershell -ExecutionPolicy Bypass -File .\scripts\init.ps1`。手动比较新旧文件，
只迁移必需的服务商值和部署值。除非现有数据库必须使用当前凭据，否则保留新生成的
数据库密钥和 JWT 密钥。

部署在反向代理后方时，设置 `PUBLIC_API_URL` 和 `PUBLIC_DASHBOARD_URL`。迁移期间
保持身份验证开启、遥测关闭。

对于内嵌 Python 记忆核心，全新用户目录默认使用 `~/.yiqiao`。如果既未设置
`YIQIAO_DIR`，也未设置旧版覆盖变量，并且 `~/.yiqiao` 尚不存在，YiQiao 会继续
使用已有的 `~/.mem0`。此兼容回退用于避免隐藏现有 `history.db` 和 `config.json`，
不会复制或删除任何目录。计划迁移状态目录时，请在验证完成后显式设置
`YIQIAO_DIR`。

为兼容旧部署，历史核心环境变量前缀仍然可以使用。新部署设置使用 YiQiao 名称。

## 数据迁移方案

### 逻辑恢复到新卷

这是首选方案，因为它会保留源部署，并使回滚更直接：

1. 使用全新空卷初始化一个隔离的 YiQiao 替代部署，但不要启动 API、控制台或
   Neo4j。
2. 按照[运维指南](OPERATIONS.zh-CN.md#恢复)中的空数据库恢复流程恢复 `postgres` 和
   `yiqiao_app`。
3. 在 Neo4j 停止时，将一致的 Neo4j 快照恢复到新的 `neo4j_data` 卷。
4. 将需要的记忆历史 SQLite 文件、导入工作区和保留的导入源复制到
   `server/history`。
5. 恢复必需密钥并启动整套服务，只允许执行比已恢复数据库更新的迁移。

### 复用克隆卷

将每个原始源卷和绑定挂载的数据目录都视为只读证据。绝不要将其连接到 YiQiao 目标
服务，也不要用数据库引擎启动它。只能复用静止快照或经过验证的克隆；这种方式比逻辑
恢复更快，但回滚风险更大。Docker Compose 卷名带有项目名称前缀，因此旧的
`server_postgres_db` 或类似名称不会自动成为新的 `yiqiao-v3_postgres_db` 卷。
进行任何更改前，使用 `docker volume inspect` 检查标签和挂载点。

只有在确认源数据目录与目标镜像使用相同 PostgreSQL 主版本、pgvector 扩展兼容，
并且目标 Neo4j 版本支持相应存储格式后，才能复用克隆卷。当前 YiQiao PostgreSQL
镜像使用 PostgreSQL 17；不能直接挂载 PostgreSQL 15 或 16 数据目录。只要版本不同
或无法确认，就应改用首选的逻辑转储与恢复方案。

不要重命名或删除源卷。创建快照或克隆卷，然后让经过审查的 Compose 覆盖配置指向
该克隆。绝不要让新旧数据库容器同时连接同一个可写数据目录。

创建替代部署前，记录每个源卷的准确名称、挂载点、Compose 项目和卷标签、存储快照
标识，以及内容校验和或备份封印。为替代部署分配唯一的 Compose 项目，并单独记录
预期的克隆名称和标签。整个迁移和验收期间，源卷必须保持停止和受保护状态。

创建替代数据库容器后、启动 API 或允许任何迁移运行前，检查解析后的容器挂载。这是
强制关卡，不能只凭目视抽查：

- PostgreSQL 和 Neo4j 的挂载源及卷名必须与登记的替代克隆或新恢复卷完全一致。
- 解析后的名称、挂载点、Compose 项目标签和 Compose 卷标签不得匹配任何登记的
  源条目。
- 替代项目标签必须等于唯一的迁移项目，卷标签必须分别标识预期的 `postgres_db` 和
  `neo4j_data` 角色。
- 任何目标 Compose 文件、渲染配置或已创建容器都不得引用原始源名称或挂载点。

保存渲染后的 Compose 配置、`docker inspect` 挂载结果和 `docker volume inspect`
标签结果作为迁移证据。缺少标签、挂载未知、版本不匹配或命中源项中的任何一种情况都
是 **NO-GO**。修正克隆或覆盖配置后重新执行关卡；绝不要为了通过检查而让源变为
可写。

### 选择性合并历史请求日志

完整恢复流程不是合并流程。只有在必须将选定的历史运维记录加入已经有数据的 YiQiao
目标时，才使用本节。所有预检和演练都必须针对隔离克隆执行。在演练通过且新的目标
快照验证完成前，不要写入在线目标。

`request_logs` 行是运维审计记录，不是记忆、嵌入向量、Qdrant 点、Neo4j 节点或图
关系。绝不要将请求日志数量报告为记忆数量，也不要根据请求日志导入成功推断记忆已经
恢复。

使用以下流程：

1. 封存每个源的逻辑导出，并创建覆盖两个 PostgreSQL 数据库、Neo4j、history 和
   必需密钥的一致目标快照。在进行任何合并写入前，证明目标快照可以隔离恢复。
2. 使用各自原始主版本，在网络隔离环境中恢复每个 PostgreSQL 源。只导出经过审查的
   表和字段；不要将 PostgreSQL 15 或 16 数据目录连接到 PostgreSQL 17。
3. 使用已记录的稳定身份键（例如规范化邮箱）清点目标和源用户，同时限制对原始身份
   数据的访问。如果一个稳定身份映射到不同用户 ID 或角色，尤其是管理员与成员不
   一致，立即以 **NO-GO** 停止。运维人员必须批准明确的角色策略并重新演练；导入器
   绝不能静默提升、降级、复制或跳过该身份。
4. 按 UUID 以及已审查源到目标字段映射的规范指纹匹配每条请求。复用的 UUID 如果
   对应不同指纹，就是冲突，因此必须 **NO-GO**。在测量重叠和冲突前，不要直接相加
   各源数量。
5. 只插入确认缺失的行。将迁移创建的每一行和每个身份记录到不可变、按运行隔离的
   自有行台账中，台账必须包含源封印和规范指纹。为所有目标预存行单独保留指纹和
   数量。
6. 针对隔离目标克隆运行两次完全相同的导入。第二次运行的插入、更新和删除数量必须
   都为零；源缺失和冲突行数量也必须都为零，并且目标预存行指纹必须保持不变。
7. 只删除台账拥有的行和身份以演练选择性回滚，然后证明目标数量和指纹恢复到快照
   基线。如果无法证明所有权，请丢弃演练克隆并使用已验证的目标快照，不要尝试部分
   回滚。

请求日志合并过程中，不要激活历史 API 密钥、刷新令牌记录、会话或其他凭据。在完成
单独的架构和安全策略审查前，将不受支持的表保留在封存归档中。

单独清点历史 Neo4j 图和 Qdrant 集合，包括准确数量、版本、向量维度、集合名称，
以及完整滚动读取或存储检查证据。当相关图或向量数据集记录数为零时，必须执行
**NO-OP**：不要创建空目标、恢复其物理存储，也不要把无关路由或配置点当作记忆。
非空图或向量数据需要单独审查迁移和身份映射，不属于请求日志合并范围。

## 嵌入兼容性

首次迁移启动时，保持原有嵌入服务商、模型和向量维度。复用向量集合时更改维度可能
导致现有向量无法读取或写入失败。如果必须更改模型或维度，请迁移到新集合，并通过
明确的迁移流程重新嵌入。

## 首次启动

运行以下命令前，先完成上述挂载解析关卡。只能从具有唯一 Compose 项目的隔离替代
检出目录运行。如果 API 会将任一数据库挂载解析到登记的源卷或目录，请以
**NO-GO** 停止；启动 API 可能应用不可逆迁移。

```bash
cd server
: "${MIGRATION_PROJECT:?Set MIGRATION_PROJECT to the reviewed unique project}"
docker compose -p "$MIGRATION_PROJECT" up -d postgres neo4j
docker compose -p "$MIGRATION_PROJECT" ps
docker compose -p "$MIGRATION_PROJECT" up -d yiqiao yiqiao-dashboard
docker compose -p "$MIGRATION_PROJECT" logs --tail=200 yiqiao
```

API 会自动应用 Alembic 迁移。迁移失败时必须停止：私下保存日志，停止新服务并调查
原因后再重试。不要将失败的迁移标记为完成，也不要绕过其修订版本。

## 验证

将客户端流量切换到 YiQiao 前，验证以下所有项目：

- API 和控制台健康端点成功响应。
- 现有管理员可以登录；只有在没有任何用户时才能创建新管理员。
- 现有项目、API 密钥、记忆、设置、Webhook、配额、请求和导出显示在正确范围内。
- 现有记忆检索返回预期结果。
- 可以使用新创建的项目 API 密钥写入并找到一条新记忆。
- 图状态健康，并且已知关系可见。
- 导入可以访问保留的源文件和工作区文件；应用数据库中存在服务端导出记录与结果；
  新的客户端下载成功。
- 完整重启 Compose 后，新旧验证记录仍然存在。

在完成上述验证和运维验收期前，保持源部署停止但完整。

## 客户端切换

尽可能将客户端改为 YiQiao API URL，并签发新的项目 API 密钥。首个版本仍提供自托管
REST 兼容路由，但非 YiQiao 托管服务的默认值、凭据和支持链接不属于 YiQiao。

进行大型聊天记录导入前，验证反向代理的请求大小和超时设置。更新 Webhook 接收端，
允许 YiQiao 来源，并通过测试投递验证当前签名请求头和密钥。

## 回滚

切换前，回滚只需停止新部署并重新启动未更改的源部署。客户端开始写入 YiQiao 后，
回滚可能导致数据丢失或分叉。请停止写入，在支持时导出增量，并明确决定如何协调数据。

如果源架构无法读取已迁移数据库，请将迁移前备份恢复到单独卷。不要让旧版本 API
连接已经迁移的生产卷。

对于选择性请求日志合并，请停止目标写入，并使用自有行台账只删除该合并创建的行。
回滚后验证目标预存行指纹。如果任何行的所有权不明确，或者无法准确复现基线，请将
已验证的目标快照恢复到新的替代部署并明确协调。绝不要通过将原始历史卷交换进目标来
回滚。
